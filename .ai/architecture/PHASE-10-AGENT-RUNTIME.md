# TASK-0058 registered specialist candidate runtime

The twelve canonical specialists have immutable v1 prompt/schema definitions and four pinned policy fixtures each. `AiAgentCatalog` resolves one exact registered version, verifies bytes against registry hashes and binds agent, schema and evaluation IDs. CI verifies old version metadata cannot change or disappear; new behavior requires a new version. No mutable `latest` alias or model-selected prompt is accepted.

The application composes a finite server-selected plan with the existing context assembler and gateway. It validates the entire plan before invocation, limits it to a configured maximum of eight steps and two explicit attempts per specialist, charges each step's reservation ceiling even after failure, and stops on unvalidated output. Every specialist receives newly assembled exact workspace/brand/run context; customer context is minimized to null. Source kinds must fit that specialist's registered memory scopes. Prior agent outputs are not inherited as trusted context. The returned receipt identifies exact prompt/context hashes, trace, route result, usage/cost and measured invocation duration. Existing gateway telemetry remains durable and contains hashes/references rather than raw context.

Candidate execution accepts only explicitly marked offline-contract routes and `AiOfflineAdapter` implementations. Live routes are rejected before invocation. Default application bindings do not enable this runtime, a provider account or a paid call. Prompts propose bounded recommendations and registered tool identifiers; execution remains a separate TASK-0057 policy/approval/idempotency path. A valid recommendation is not a validated segment AST, executable journey graph, send approval or deployable connector.

`AiEvaluationReport` computes immutable policy outcomes from every pinned case; there is no constructor that accepts a model-provided pass flag. Missing, extra, duplicate or failing cases deny promotion. The report records `offline_contract` evidence and cannot represent semantic model-quality measurements. `AiPromptPromotionGate` binds exact candidate/report/scope hashes and requires a currently verified independent human reviewer through a trusted authority dependency. Candidate author, requesting actor and the specialist cannot self-approve. The same checks apply when selecting a previously evaluated version for rollback. There is no permissive default authority or automatic registry/alias mutation: reviewed code changes carry an authorized offline receipt. Live/production promotion is always rejected by this gate.

The fixtures establish schema, grounding-ID, refusal, isolation and governance behavior. They do not establish the factual correctness of arbitrary prose, commercial rights, actual specialist task quality, provider latency/cost, production throughput or exhaustive prompt-leak detection. Live semantic evaluation, account-specific privacy/rights evidence, owner-reviewed thresholds and canary evidence remain necessary before live activation. No acceptance criterion is removed and no offline result is relabeled as provider evidence.

No dependency, database migration, HTTP endpoint, UI surface or production handler is introduced. The locked application/static/architecture/security/PostgreSQL/PHP-floor/E2E gates remain required.
