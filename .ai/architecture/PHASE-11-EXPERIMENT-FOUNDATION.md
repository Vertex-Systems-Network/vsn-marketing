# Phase 11 experiment assignment foundation — TASK-0063

Scope: offline, provider-neutral foundation. No route, public API, automated send, production enrollment, outcome analysis or default exposure verifier is registered.

- A versioned plan is represented by an immutable SHA-256 canonical configuration (workspace, optional brand, layer, unit kind, control/holdout, weights summing to 10,000 basis points). Creation stores a draft; a different actor with campaign approval permission activates it. The application never edits an active plan. Tampering changes its fingerprint and denies assignment.
- Stable randomized unit identity is an opaque HMAC digest scoped to workspace, brand, layer and unit kind. A separate HMAC draw incorporates the plan fingerprint. Rejection sampling avoids modulo bias for the 10,000 basis point allocation. The server key must be at least 32 bytes and is supplied separately; a fingerprint binds an existing plan to its key, so unplanned rotation denies assignment.
- An immutable layer-key registry prevents a new experiment under the same scope/layer from silently switching its HMAC key. A workspace/layer/subject unique key makes concurrent experiments in the same layer mutually exclusive. An experiment/subject unique key and insert-or-ignore with post-read give idempotent replay. PostgreSQL contention is verified by a forked integration test in CI; SQLite feature tests alone do not certify contention.
- Assignment is not exposure. `recordExposure` requires a separately injected `ExposureVerifier` witness for the exact scope, assignment, variant, reference and time. Holdout exposure is denied; repeat treatment references return the same evidence row. No production verifier implementation is registered here, so no live exposure call is authorized until TASK-0064 binds a trusted render/send event.
- Existing workspace campaign permissions are reused through `WorkspaceAuthorizer`; the service requires an actor context, checks brand ownership at creation, and exact workspace/nullable-brand predicates for each read. A new experiment-specific permission taxonomy needs a separate governance decision. Raw contact identifiers are not stored by this ledger, but pseudonymous digest data still needs retention/deletion policy before live rollout.
- Additive migration creates four tables with workspace-bound composite FKs. Rollback refuses any row in any table before dropping; no destructive or backfill operation is performed.

Unproven: actual user exposure, conversion lift, production statistical power, real campaign eligibility and live scale. TASK-0064/0066 must integrate and measure these before a winner can be certified.
