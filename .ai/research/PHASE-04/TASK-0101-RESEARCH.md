## Material findings

### 1. Five minutes is the minimum supported scheduled interval

GitHub documents that scheduled workflows can run no more frequently than once every five minutes. Scheduled execution targets the latest default-branch commit. GitHub also warns that scheduled runs can be delayed during high load and may occasionally be dropped. Therefore the persistent Supervisor must combine a five-minute heartbeat with event-driven triggers; the cron is a reconciliation safety net, not a real-time guarantee.

Disposition: **acceptance criterion / runtime design**.

### 2. The workflow must exist on the default branch for schedule and workflow_run behavior

Scheduled workflows run from the default branch, and `workflow_run` triggering also requires the workflow file to exist on the default branch. The Supervisor therefore becomes truly persistent only after its PR is merged to `main`.

Disposition: **deployment constraint**.

### 3. Privileged PR triage should use pull_request_target only with trusted base code

GitHub documents `pull_request_target` as running in the base/default-branch context and explicitly identifies authenticated PR labeling/commenting/triage as a legitimate use case. GitHub also warns that checking out and executing PR-head code from such a privileged workflow creates a pwn-request risk. The persistent Supervisor therefore uses `pull_request_target`, explicitly checks out `main`, and never fetches or executes PR-head files. PR titles, bodies, branches, and comments are API data only.

Disposition: **security requirement / trigger design**.

### 4. GITHUB_TOKEN suppresses most recursive workflow-trigger chains

GitHub documents that events generated by actions authenticated with the repository `GITHUB_TOKEN` generally do not create new workflow runs, with documented exceptions such as `workflow_dispatch` and `repository_dispatch` and special handling for some pull-request activity. This is useful for a Supervisor that writes status comments/issues because those writes should not form an infinite self-trigger loop.

Disposition: **security/reliability control**.

### 5. Concurrency should collapse stale Supervisor reconciliations

GitHub's `concurrency` key can ensure only one reconciliation is active and can cancel obsolete in-progress runs when a newer event arrives. A repository-wide constant Supervisor concurrency group with `cancel-in-progress: true` is appropriate because each run recomputes state from GitHub rather than applying an ordered mutation log.

Disposition: **runtime design**.

### 6. Least privilege is required

GitHub's secure-use guidance recommends least-privilege credentials. The persistent Supervisor only needs `contents: read`, `actions: read`, `pull-requests: read`, and `issues: write`. It must not receive contents write, deployments, packages, environments, statuses/check mutation, administration, or secret-management permissions. Product/runtime code and canonical `.ai` ledger state remain outside the workflow's mutation authority.

Disposition: **security requirement**.

### 7. Completion and readiness evidence must be deterministic and fail closed

Completion recognition is an exact standalone-line comparison against the repository-defined `Work Done and Submitted` signal. A registered PR is review-ready only when it is non-draft, targets main, comes from the registered repository branch, carries the standalone workstream marker and completion signal, contains current main in its history, and has successful latest runs for all required workflows on that exact head SHA. Missing API evidence is failure, never inferred success.

Disposition: **parser/readiness requirement**.

### 8. workflow_run is useful for exact-head CI reconciliation but must remain bounded

The `workflow_run` event exposes completed workflow activity and defaults to the default-branch execution context. The Supervisor uses it only as a trigger to recompute PR CI state through the API rather than trusting event payload conclusions. The workflow does not launch another CI chain; it observes and writes durable coordination status.

Disposition: **runtime design**.

## Repository-specific design conclusion

Implement one immutable-action-pinned GitHub Actions workflow with:

- `schedule` at `*/5 * * * *`;
- `workflow_dispatch`;
- relevant `pull_request_target` activity using trusted default-branch code only;
- `issue_comment: created`;
- `workflow_run: completed` for core CI workflows;
- one constant concurrency group with stale-run cancellation;
- explicit least-privilege permissions;
- deterministic standard-library Python GitHub REST inspection;
- one durable `[Supervisor] Persistent Control Plane Status` issue;
- exact standalone completion-signal parsing;
- current-main ancestry verification before review-ready status;
- latest exact-head CI classification;
- a deduplicated exact-head `SUPERVISOR REVIEW READY` marker that is explicitly not approval;
- no merge, ref mutation, branch protection change, canonical state mutation, product-code mutation, or worker impersonation.

Policy tests are executed by the existing read-only AI Continuity Guard so proposed changes are tested on PR heads without giving PR code the persistent Supervisor's write-capable coordination token.
